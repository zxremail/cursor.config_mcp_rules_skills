# 驱动小组周报总结表格生成规范

当用户提供驱动小组成员的周报并要求整理为小组总结表格时，必须遵循以下所有规则。

---

## 1. 总体原则

- 从**小组整体角度**进行总结，而非个人视角。
- **不包含任何成员姓名**，只保留任务内容本身。
- 将不同成员对同一项目的工作**合并到同一条目**下。
- 表格只有三行任务分类：**重点项目开发**、**技术选项与优化**、**问题定位与支持**。
- **禁止**再输出「调试测试文档」这一行（含同义改名：文档输出、测试文档、交付物等）。测试报告、方案、立项材料、教程等一律并入上述三类中对应项目，不得另开第四行。

## 2. 输入来源

- 输入为驱动小组三位成员（朱兴瑞、王霆、朱日芃）的个人周报。
- 输入格式通常为按负责人分列的"本周任务"和"下周任务"。
- 输入来源可以是：Markdown 文件、截图、飞书文档链接。
- 飞书文档链接优先用 `lark-cli docs +fetch --doc "<URL>" --as user` 拉取；`document_id` 从 URL 路径末段提取。
- 拉取后必须扫描 `<cite ...>`。源里的文档引用要原样保留 `doc-id`、`file-type`、`title`，写入输出；禁止改成《标题》纯文字。

## 3. 输出要求

每次生成**两份输出**：

### 3.1 本地 Markdown 文件

- 文件命名格式：`驱动小组周报表格_MMDD.md`（`MMDD` 为周报对应日期）。
- 使用 Markdown 表格语法。
- 文档写成可点击链接：`[标题](https://rigolportal.feishu.cn/wiki/<wiki_token>)`（docx 则用 `/docx/<obj_token>`）。

### 3.2 飞书云文档

- 使用 `lark-cli docs +create --title "驱动小组周报表格_MMDD" --doc-format xml --content "@xxx.xml" --as user` 创建。
- 已有文档用 `lark-cli docs +update --doc <id> --command overwrite --doc-format xml --content "@xxx.xml" --as user`。
- **必须使用 DocxXML `<table>` + `<ul>/<li>`**，文档引用用 `<cite type="doc" doc-id="TOKEN" file-type="wiki"/>`（与源一致；源是 wiki 就保留 wiki token）。
- 生成后返回飞书文档链接，并抽查 fetch 结果中仍含 `<cite doc-id=...>`。

## 4. 表格结构

表格固定为**三列、三行分类**（不要第四行）：

| 任务分类 | 本周任务汇总 | 下周任务安排 |
|----------|--------------|--------------|
| 重点项目开发 | ... | ... |
| 技术选项与优化 | ... | ... |
| 问题定位与支持 | ... | ... |

## 5. 任务分类定义

### 5.1 重点项目开发

核心产品项目的开发与推进，以及该项目直接产出的测试/分析文档，包括但不限于：

- 系统移植与适配（如 RK3588 RIGOLOS）
- 产品项目开发（如草原雕 II、金雕、玄铁重剑、大山雀、白尾雷鸟等）
- 驱动移植（PCIe、SDIO、LCD、Touch 等）
- MCU 固件开发与升级
- 产品测试交付、上电/适配分析文档、上线介绍、HAL/网卡等测试文档

### 5.2 技术选项与优化

技术方案调研、代码优化、立项与方案文档，包括但不限于：

- 技术方案调研与文档（如扩屏方案、USBTMC 方案、LXI/CRA 调研）
- 立项材料、预自检报告、实现方案技术文档
- MCU 模板优化（升级功能、日志功能、FPGA 下载等）
- HAL 库优化与适配、代码框架整合与重构

### 5.3 问题定位与支持

Bug 定位、客户问题处理和跨项目技术支持，以及对应的定位记录/支持文档，包括但不限于：

- 客户问题处理（如华为 DS7W 等）
- 硬件问题定位（如通信异常、枚举失败等）
- 跨项目协助与技术支持、压测问题联调
- 问题定位报告、联调记录、支持手册

### 5.4 文档如何归类（原「调试测试文档」拆分）

源周报里的文档、报告、教程**不要单独成行**，按所属项目并入 5.1–5.3：

| 文档类型 | 归入 |
|----------|------|
| 立项材料、调研报告、方案草稿、标准/认证技术文档 | 技术选项与优化 |
| 产品测试报告、上电/适配分析、上线介绍、HAL/测试文档、操作教程 | 重点项目开发 |
| 问题定位报告、联调记录、客户支持手册 | 问题定位与支持 |

- 同一项目的文档条目与开发/调研任务合并到同一 `**项目名称**` 下。
- 同一 `cite` 已出现在该项目条目中，不要再复制一份。
- 拆分后逐条核对源里每一份文档引用，禁止遗漏。

## 6. 内容格式规范

### 6.1 层级结构

每个分类下按**项目名称**分组，项目下列出具体任务条目；文档链接跟在对应任务后：

```
• **项目名称**：
    - 具体任务 1
    - 具体任务 2：<文档引用>
```

### 6.2 无内容处理

若某分类下本周或下周无对应任务，填写 `-`。

### 6.3 本地 Markdown 文件格式

- 使用 `<br>` 实现表格单元格内换行。
- 使用 `<br><br>` 分隔不同项目。
- 使用 `&nbsp;&nbsp;` 实现子条目缩进。
- 项目名称使用 `**加粗**` 显示。
- 文档用 Markdown 链接，不用《书名号》纯文字。

示例：

```markdown
| **重点项目开发** | • **RK3588 RIGOLOS 适配**：<br>&nbsp;&nbsp;- PCIe 控制器驱动移植完成<br><br>• **草原雕**：<br>&nbsp;&nbsp;- 上电链路及耗时分析：[草原雕 COME 上电流程耗时梳理](https://rigolportal.feishu.cn/wiki/PiEEwMighiT9ZukDryMc646unug) | • **RK3588 RIGOLOS 适配**：<br>&nbsp;&nbsp;- SDIO 控制器驱动移植适配 |
```

### 6.4 飞书文档格式（DocxXML）

用 DocxXML 表格；单元格内用 `<ul>/<li>`。源文档引用写成：

```xml
<li>立项材料草稿：<cite type="doc" doc-id="VPYpwPv5riXWhYkcKE4c3oNBnWc" file-type="wiki"/></li>
```

- 表头 `<th>` 可加 `background-color="light-purple"`、`align="center"`。
- 第一列（任务分类）居中；文档引用禁止改成《标题》文本。
- **禁止**用 `--doc-format markdown` 塞 `lark-table`（会丢正文）；用 `--doc-format xml`。
- 写入后 `docs +fetch` 确认 `<cite doc-id=... file-type="wiki" title="...">` 仍在。

## 7. 常见错误

| 错误 | 正确做法 |
|------|----------|
| 仍输出「调试测试文档」第四行 | 只有三行分类；文档并入对应项目 |
| 文档改成《标题》纯文字 | 保留 `<cite>` / Markdown 链接 |
| 拆分类后漏掉某份文档 | 对照源 `<cite>` 逐条勾掉 |
| 同一文档在两类里重复出现 | 只留在归属项目下一次 |
